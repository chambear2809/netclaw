# Phase 0 Research: Mobile Release Readiness

## R1: The App Store review rejection history (FR-006)

NetClaw Mobile's actual submission history, in order, each rejection's guideline, root cause, and
the artifact that fixed it:

| # | Guideline(s) | Issue | Root cause | Fix |
|---|---|---|---|---|
| 1 | 2.3.3 (Accurate Metadata) | iPhone/iPad screenshots showed only the onboarding/splash screen | Only pre-enrollment screens had been captured; Apple explicitly rejects "splash and login screens" as not showing the app in use | Replaced with real in-use screenshots (Dashboard, Feed, Chat, Approvals) captured from a real enrolled device |
| 1 | 1.5 (Safety — Developer Info) | Support URL was a bare GitHub issues link | No framed "how to get help" page, just a raw tracker URL | `docs/support.html`, published to GitHub Pages, with actual support guidance |
| 1 | 2.1 (Information Needed) | Reviewer had no way to test a self-hosted-Border app | No instructions or demo material provided | `docs/APP-REVIEW-NOTES-DRAFT.md` (usage instructions) + `docs/APP-REVIEW-REPLY-5.1-DRAFT.md`-style reply referencing existing demo videos |
| 2 | 2.1(a) / 2.1 | Reviewer asked for a demo QR code and a demo video on a physical device | Same root cause as above, pressed further | Existing YouTube demo videos (iPhone, Watch) referenced in App Review Notes; live production Border access deliberately NOT granted (security tradeoff) |
| 3 | 5.1.1(i) / 5.1.2(i) (Privacy — Data Collection/Use) | App sends user questions and captures to an AI model with no disclosure or consent | `docs/privacy-policy.html` never disclosed the AI-forwarding behavior; no in-app consent gate existed | `onboarding_explainer_screen.dart` consent checkbox (required before "Agree and Continue") + a new privacy policy section identifying what's sent, to whom (the operator's own chosen AI provider — third-party or fully local/offline), and when |

Separately, real build-breaking issues surfaced while producing release builds (not App Review
rejections, but part of the same release-engineering effort, per FR-007):

- `scripts/mobile-release-archive.sh` had a hardcoded free-vs-paid Apple team ID guard that became
  permanently stale once this project's account upgraded to a paid Program under the *same* team
  ID (common for an individual Apple Developer account) — removed; `ExportOptions.plist`'s
  placeholder team ID was filled in with the real one.
- The same script needed `-allowProvisioningUpdates` on both `xcodebuild archive` and
  `-exportArchive`, because Xcode's automatically-managed App Store distribution profiles lagged
  behind capabilities added in specs 111/114 (Siri, App Groups, Time Sensitive Notifications), and
  the widget extension target had no Store profile registered at all yet.
- Flutter's generated `FlutterGeneratedPluginSwiftPackage/Package.swift` hardcoded an iOS 13.0
  platform minimum regardless of the project's real 16.2 floor, conflicting with Firebase's SPM
  packages (which now require iOS 15+) — patched directly in the ephemeral generated file
  (regenerated by tooling, not a tracked source file).

## R2: How mobile enrollment actually works today (grounds User Story 1)

The full manual procedure is already documented in `mobile/netclaw-mobile/MOBILE-ONBOARDING.md`,
written after a real first install hit five independent blockers, each masking the next. The
"fast path" it documents:

```bash
netclaw risk edge-check                       # 0. what's missing? (checks everything below)
netclaw risk role border <risk-name> in2n     # 1. standalone -> Border, in2n stack on
systemctl --user restart netclaw-mesh.service # 2. apply the role/stack change
netclaw risk edge-check                       # 3. confirm green before going further
netclaw risk token --edge <device-label>      # 4. mint the QR
netclaw risk members                          # 5. verify the device that claimed it
```

**Decision**: the installer's new enrollment prompt (User Story 1) calls this exact existing
sequence — `netclaw risk edge-check` first (to detect and explain what's missing per FR-004), then
the role/stack promotion + restart only if not already a Border, then `netclaw risk token --edge`.
It does not reinvent enrollment; it automates a sequence an operator would otherwise have to
discover and run by hand from a separate markdown file.

**Rationale**: `MOBILE-ONBOARDING.md` already represents hard-won operational knowledge (five real
blockers found on a real install: role, stack, missing `websockets`/`qrcode` under the daemon's
actual interpreter, port-forwarding, and a stale-journal false positive). Reusing its exact
sequence, rather than approximating it, avoids reintroducing any of those five.

## R3: When does a restart/reload cycle actually matter? (clarifies FR-005a/FR-005b)

Investigating whether *every* enrollment needs a service cycle, or only some:

- **A restart IS needed** when the role changes (`standalone` → `border`) or the `in2n` stack gets
  enabled for the first time, or `N2N_CLAW_DOMAIN`/`N2N_EDGE_WS_PORT` change — these are read once
  at daemon startup (`netclaw-mesh.service`'s `ExecStart` environment). This happens at most once
  per Border, typically during first-time setup.
- **A restart is NOT needed** for minting an additional `--edge` token or enrolling an additional
  device once the Border is already correctly configured and its edge listener is already bound —
  the already-running daemon accepts new WebSocket connections and mints new member rows live, with
  no reload.

**Decision**: FR-005a's "installer triggers enrollment only after Border/Risk services are
confirmed running" refers to the *initial* first-time-install case, where role promotion and a
restart are a real, one-time part of the sequence (R2's steps 1-2) — not a claim that every future
enrollment needs a cycle. FR-005b's "may require a gateway/daemon reload cycle" is conditional on
whether role/stack/env actually changed, which the installer already knows (it just performed
that promotion, or didn't need to).

## R4: What "SOUL/memory/heartbeat/risk awareness" actually means here

Investigating whether the agent's own self-model needs an update after an enrollment:

- `SOUL.md` is static identity/principles content — not something enrollment events rewrite, and
  this feature does not propose making it dynamic.
- Federation/member state (`netclaw risk members`, `netclaw risk status`) is already live,
  queryable data in the mesh daemon's own database — not something that goes stale absent a
  restart, once the daemon itself is up.
- The existing `n2n-federation` skill (`workspace/skills/n2n-federation/SKILL.md`) gives the agent
  federation-awareness tools (`n2n_member_add`, `n2n_knowledge_route`, etc.) for federation
  *members* (peer Borders), but nothing found in it specifically surfaces edge/mobile-device
  enrollment state as something the agent is prompted to mention or reason about.

**Decision**: no SOUL.md or static-file rewrite is needed or proposed. What this feature actually
needs to confirm/close (tasks.md) is narrower: that the agent has *some* tool-level path to answer
"is a mobile device enrolled right now" if asked (even indirectly, via existing federation
tooling) — and if that path doesn't exist today, exposing `netclaw risk members`/`status` as an
agent-callable tool is the concrete, scoped gap, not a broader "make the agent self-aware" claim.

## R5: Where the new installer prompt belongs (corrected after reading the actual script)

`scripts/install.sh` (716 lines) already has a clear tail sequence: Summary → DefenseClaw opt-in
(interactive) → "Launch NetClaw Platform Setup" (runs `scripts/setup.sh` for network platform
credentials, gated on `tui_is_tty`) → Next Steps → Problem report.

`scripts/peering-setup.sh` is a BGP-mesh-peering wizard (AS numbers, ngrok peers,
`NETCLAW_MESH_*` env vars) that ends by starting/restarting the daemon (`daemon_start`, its own
existing `ask_yn` prompt at the "restart it now?"/"start it now?" branch). **Correction to an
earlier draft of this research**: this wizard does *not* configure `N2N_ROLE`/Risk name/NCFED
stacks at all — that promotion (`netclaw risk role border <name> in2n`) is a wholly separate action
via `scripts/netclaw`'s own `risk_role()` function, hitting `/n2n/risk` directly. The two are
independent: an operator can run the mesh wizard without ever becoming a Border for mobile
purposes, and becoming a Border for mobile purposes doesn't require running the mesh wizard.

**Decision**: to avoid duplicating the edge-check → promote-role-if-needed → mint-token sequence
in two places, `scripts/netclaw`'s new `risk_enroll_mobile()` (research R2, FR-005) becomes the
**single canonical entry point** for "make mobile enrollment happen," including the previously
missing role-promotion step: it runs `edge-check`, and if the result is `not_border` or
`stack_disabled`, it now offers *inline* to promote (asking for a Risk name if one isn't already
set, then calling the existing `risk_role()` logic and `daemon_start`) before re-checking and
minting a token. `scripts/peering-setup.sh`'s new prompt, added right after its own `daemon_start`
call succeeds, does nothing but ask "enroll a mobile device now?" and — if yes — shell out to
`"$NETCLAW_DIR/scripts/netclaw" risk enroll-mobile`, so the actual logic lives in exactly one
place and the installer-side integration is a thin, five-line delegation.
